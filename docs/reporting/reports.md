# Reports

`ai-surface report` (`internal/reporting` + `internal/service/reporting`)
builds structured, versioned, citation-validated reports from Phase
2-13's own already-persisted data. No report type duplicates any
existing model — every section is assembled by reading Phase 2/8/9/10/
11/12/13's own repositories directly.

## Report types

| Type | Subject required | Built from |
| --- | --- | --- |
| `investigation` | yes (investigation id) | investigation + evidence + timeline |
| `asset` | yes (asset id) | asset + its findings + latest risk score |
| `correlation` | yes (correlation id) | correlation + graph nodes/edges + attack chain |
| `attack_surface` | no | `internal/analytics.AttackSurface`/`Assets` |
| `detection` | no | `internal/analytics.Detections` |
| `executive` | no | `internal/analytics.Overview`/`Posture`/`Risk`/`AttackSurface` |
| `audit` | no | every investigation's own timeline within range (this platform's existing audit trail — see "Audit report" below) |

## Lifecycle

```
draft (AI-assisted only) ──┐
                            ├──► generated ──► reviewed ──► approved
(fully deterministic) ─────┘
```

Every report generated by this phase today is fully deterministic — no
Phase 13 AI narration is embedded yet (a documented Known Limitation;
the domain model's `Provider`/`Model`/`PromptVersion` fields and
`StatusDraft` already exist for a future phase to use). A deterministic
report therefore always starts at `generated`, never `draft`.
`ai-surface report review <id>` moves it to `reviewed`;
`ai-surface report approve <id> --approver <name>` is the only path to
`approved`, and requires an actor (phase14.md §40) — approving an
already-approved report is rejected, never silently re-recorded.

## Versioning

`domainreporting.Report.Version` mirrors `rule.Version`'s exact pattern
from Phase 11: one `(target_id, report_type, subject_id)` triple's
reports form a sequential version series (`reports_version_unique`'s
`NULLS NOT DISTINCT` index so target-wide types, whose `subject_id` is
`NULL`, are deduplicated correctly too). `ai-surface report create`
computes `LatestVersion + 1` and always inserts a new row — regenerating
never overwrites an earlier version (phase14.md §77). Report content is
otherwise immutable once created; `Approve` is the sole permitted
mutation, and it only ever touches the approval columns, never `Content`
or `ContentHash`.

## Report content and citations

A report's `Content` is a JSON `Envelope` (`internal/reporting.Envelope`)
holding its rendered `Sections` (title/body/citations) and the full
evidence-reference list every citation must be drawn from. Citations
reuse Phase 13's exact `[type:id]` bracketed token convention
(`ai.Fact.Citation`) — `internal/reporting.ValidateSections` calls
`internal/ai.ValidateCitations` directly, so a fabricated evidence
reference is always stripped before a report is ever persisted
(phase14.md §92), the identical discipline Phase 13's own AI responses
already apply.

## Integrity

`ContentHash` is a SHA-256 hash of `Content`, computed once at
generation (phase14.md §41) — later verification that a report row
wasn't modified outside this platform's own write path, never an
authentication mechanism.

## Export

`ai-surface report export <id> --format json|csv`:

- **JSON**: the full `Envelope`, re-marshaled with Go's
  `encoding/json` (which HTML-escapes `<`, `>`, `&` by default — see
  `internal/reporting/json_test.go`'s `TestEncodeJSON_EscapesHTMLByDefault`
  for why this alone satisfies phase14.md §94 for the JSON path).
- **CSV**: one row per section (`section`, `body`, `citations`),
  encoded with the standard library's `encoding/csv` (correct comma/
  quote/newline/Unicode handling) and every cell passed through
  `EscapeCSVValue` first — a leading `=`, `+`, `-`, `@`, tab, or carriage
  return is prefixed with a single quote, the OWASP-recommended
  mitigation for spreadsheet formula injection (phase14.md §95/§106).

Both paths redact secrets via `internal/ai.Redact` — reused directly
rather than re-implemented (phase14.md §90) — applied once at generation
and again at export time (defense in depth, the same two-layer pattern
`internal/ai.ValidateOutput` already uses for AI provider responses).

## Content security

This platform renders no HTML anywhere — there is no template engine, no
web frontend, no markup surface for untrusted telemetry to be injected
into. "XSS protection" (phase14.md §93/§94) is therefore satisfied
structurally: report bodies are always plain text, JSON escaping handles
the JSON export path, and CSV values are never interpreted as anything
but spreadsheet cell text once escaped. No custom report-template
upload mechanism exists (phase14.md §96) — sections are built entirely
by this platform's own Go code, never from an analyst-supplied template.

## Audit report

Reuses the investigation timeline as this platform's existing audit log
— the same "these ARE the audit trail" precedent Phase 9/11/12/13 each
already established for their own audit requirements — rather than a new
audit table. `ai-surface report create --type audit` walks every
investigation's timeline events within the requested range and renders
`timestamp / actor / action / resource / description` lines.

## Authorization

No auth/RBAC layer exists anywhere in this platform (confirmed by
inspection). `TargetID` scoping is the boundary: every report-building
function checks the resolved subject's own `TargetID` against the
request's target and rejects a mismatch (`apperrors.NewForbidden`) —
see `internal/service/reporting/sections.go`.
